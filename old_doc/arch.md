# Sextant — 群聊多 Agent 协作架构

> 本文档描述 Sextant 的**群聊协作模型**——一种去中心化、会话驱动的多 Agent 交互范式。
> 与 PLAN.md 中的 Leader-Worker 流水线模型互补：
> - **群聊模型** → 探索性讨论、需求澄清、方案辩论（「聊清楚要做什么」）
> - **Leader-Worker 模型** → 确定性执行、任务分发、编码/审查/测试（「把事做完」）

---

## 一、两种模型的关系

```
┌──────────────────────────────────────────────────┐
│                 Sextant                            │
│                                                    │
│  ┌──────────────┐          ┌──────────────────┐   │
│  │  群聊模型      │  自然语言  │  Leader-Worker   │   │
│  │  (讨论阶段)    │ ───────→ │  (执行阶段)       │   │
│  │              │  task_spec│                  │   │
│  │  - 广播 + @    │          │  - Leader 调度    │   │
│  │  - 自组织      │          │  - Worker 执行    │   │
│  │  - 辩论/澄清   │          │  - 上下文隔离     │   │
│  └──────────────┘          └──────────────────┘   │
│                                                    │
│  同一个框架核心：Agent 定义可插拔，角色边界可复用    │
└──────────────────────────────────────────────────┘
```

**两种模型共享**：Agent 角色定义、上下文隔离规则、LLM 适配层。

## 二、群聊模型 —— 核心交互范式

### 2.1 基础交互：广播 + 自组织回复

```
人类 ZP 发送消息（默认广播）
       │
       ├──→ Agent A  相关性判断  →  决定回复 / 沉默
       ├──→ Agent B  相关性判断  →  决定回复 / 沉默  
       ├──→ Agent C  相关性判断  →  决定回复 / 沉默
       └──→ Agent D  相关性判断  →  决定回复 / 沉默
```

**人类消息默认对所有 Agent 可见。** 每个 Agent 独立判断「这条消息跟我有关系吗？我该发言吗？」

**被 @ 的 Agent 强制回复**，跳过相关性判断。

### 2.2 关键交互模式

#### 模式 A：自由讨论
```
人类：我想设计一个 benchmark，对比 acp 和 cp 的性能，你们都聊聊
      ↓ 广播
Agent A(测试)：我来设计场景（高相关性 → 发言）
Agent B(PM)   ：先搞清楚 ZP 的真实意图（观察到歧义 → 插嘴）
Agent C(acp)  ：沉默，等待更多上下文
Agent D(cp)   ：沉默，等待更多上下文
```

#### 模式 B：定向提问
```
人类：@Agent A 你设计的场景里，文件数量怎么定的？
      ↓ 解析 @mention
Agent A：强制回复（被 @ 了）
Agent B：可能插嘴补充
Agent C：继续沉默
```

#### 模式 C：Agent 间辩论
```
Agent A：我建议用 1000 个小文件
Agent C：等等，acp 在 1000 个文件场景体现不出优势，建议 10000+
Agent A：@Agent C 你没说到点。关键不是文件数量，是 fsync 策略差异
Agent B：停一下，我们先定评判标准再讨论参数
```

**Agent 可以互相 @、反驳、补充。** 不需要人类主持。

### 2.3 会话生命周期

```
创建群聊 session
    │
    ├─ 人类发布开发任务描述
    │       │
    │       ▼
    │  讨论阶段（群聊模型）
    │  - Agent 参与讨论、澄清需求、辩论方案
    │  - 人类在群里随时纠正方向
    │  - 输出：达成共识的任务描述
    │       │
    │       ▼
    │  执行阶段（触发 Leader-Worker 模型 或 手动编码）
    │  - Leader 将共识转化为 task_spec
    │  - Worker 执行编码/审查/测试
    │  - 执行结果推回群聊
    │       │
    │       ▼
    │  验收阶段（群聊模型）
    │  - 人类审查结果
    │  - Agent 解释实现细节
    │  - 人类确认完成 / 提出修改
    │       │
    │       ▼
    │  session 关闭，上下文归档
```

## 三、架构设计

### 3.1 整体架构

```
┌─────────────────────────────────────────┐
│              群聊界面 (UI)                │
│   人类 ZP  │  Agent A  │  Agent B  │ ...  │
└────────────────┬────────────────────────┘
                 │ 新消息到达
                 ▼
┌─────────────────────────────────────────┐
│           消息分发器 (Router)              │
│                                          │
│  职责：                                   │
│  - 解析 @mentions                        │
│  - 广播新消息给所有 Agent                  │
│  - 收集 Agent 回复，推送到群聊             │
│  - 处理并发回复的时序                      │
└────┬────────────────────────────────────┘
     │ 并行分发
     ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Agent A      │  │  Agent B      │  │  Agent C      │
│  (测试工程师)  │  │  (项目经理)    │  │  (acp 专家)   │
│              │  │              │  │              │
│ 内部状态：     │  │ 内部状态：     │  │ 内部状态：     │
│  角色定义      │  │  角色定义      │  │  角色定义      │
│  观察摘要      │  │  观察摘要      │  │  观察摘要      │
│  工具集        │  │  工具集        │  │  工具集        │
│  相关性阈值    │  │  相关性阈值    │  │  相关性阈值    │
└──────────────┘  └──────────────┘  └──────────────┘
```

### 3.2 消息分发器（Router）

```
def on_message(msg: Message, session: Session):
    mentions = parse_mentions(msg.content)
    
    # 广播消息给所有 Agent
    responses = []
    for agent in session.agents:
        is_mentioned = agent.id in mentions
        
        # 并行执行每个 Agent 的决策
        response = agent.handle_message(
            message=msg,
            session_history=session.history,
            is_mentioned=is_mentioned
        )
        
        if response.should_speak:
            responses.append(response)
    
    # 按到达顺序推入群聊
    for resp in sorted(responses, key=lambda r: r.timestamp):
        session.push_message(resp)
```

### 3.3 Agent 内部结构

每个 Agent 由三个组件组成：

```
┌────────────────────────────────────────────┐
│              Agent 实例                      │
│                                             │
│  ┌─────────────────────────────────────┐   │
│  │         角色定义 (Role Spec)          │   │
│  │  - 身份/性格/说话风格                  │   │
│  │  - 专业领域和知识边界                   │   │
│  │  - 可访问的工具集                      │   │
│  │  - 上下文范围（全局 / 任务级）           │   │
│  └─────────────────────────────────────┘   │
│                                             │
│  ┌─────────────────────────────────────┐   │
│  │        观察摘要 (Observation Summary)  │   │
│  │  - 当前会话的关键事实                   │   │
│  │  - 已做出的决策                        │   │
│  │  - 未解决的争议                        │   │
│  │  - 潜在的发言触发点                     │   │
│  └─────────────────────────────────────┘   │
│                                             │
│  ┌─────────────────────────────────────┐   │
│  │     相关性判断器 (Relevance Judge)     │   │
│  │  - 输入：新消息 + 观察摘要 + 角色       │   │
│  │  - 输出：{ should_speak, confidence,  │   │
│  │            reason, priority }         │   │
│  │  - 使用低成本模型（nano 级）            │   │
│  └─────────────────────────────────────┘   │
│                                             │
│  ┌─────────────────────────────────────┐   │
│  │     回复生成器 (Response Generator)    │   │
│  │  - 输入：完整对话历史 + 观察摘要        │   │
│  │  - 输出：回复文本                      │   │
│  │  - 使用主力模型                         │   │
│  └─────────────────────────────────────┘   │
└────────────────────────────────────────────┘
```

### 3.4 Agent 决策流程

```
新消息到达
    │
    ▼
┌─────────────────────────┐
│ 更新观察摘要              │
│ - 提取新事实              │
│ - 更新关键决策记录         │
│ - 检测矛盾/遗漏           │
└──────────┬──────────────┘
           ▼
┌─────────────────────────┐
│ 相关性判断 (nano 模型)    │
│                         │
│ 输入 prompt:            │
│  你是 [角色名]，        │
│  擅长 [专业领域]。      │
│  当前讨论主题：[摘要]    │
│  新消息：[内容]          │
│                         │
│  判断：                  │
│  1. 这条消息跟你的       │
│     专业领域相关吗？     │
│  2. 你能提供有价值的     │
│     补充/纠正/质疑吗？   │
│  3. 你观察到需要立即     │
│     指出的问题吗？       │
│                         │
│  输出 JSON:             │
│  {                      │
│    "should_speak": bool,│
│    "confidence": 0-1,   │
│    "reason": "..."      │
│  }                      │
└──────────┬──────────────┘
           ▼
    should_speak = false
    → 结束（保持沉默，观察摘要已更新）
    
    should_speak = true
           │
           ▼
┌─────────────────────────┐
│ 回复生成 (主力模型)       │
│                         │
│ 输入：完整对话历史        │
│      + 角色定义          │
│      + 观察摘要          │
│      + 我的判断理由      │
│                         │
│ 约束：                   │
│ - 精简，只说必要的        │
│ - 如果别人已经说了        │
│   同样的意思 → 不重复     │
│ - 可以 @ 其他 Agent      │
└──────────┬──────────────┘
           ▼
        回复内容
```

### 3.5 相关性判断的 Prompt 模板

```
system: |
  你是一个轻量级的相关性判断器。你的任务是判断一条群聊消息是否与你的专业领域相关。

  你的角色：{role_name}
  你的专长：{expertise}
  当前对话摘要：{observation_summary}

  规则：
  - 如果消息直接 @ 你 → should_speak = true, confidence = 1.0（但此情况已在代码层处理，你不会收到此判断请求）
  - 如果消息涉及你的专长领域且你能提供独特价值 → should_speak = true
  - 如果其他 Agent 已经表达了完全相同的观点 → should_speak = false
  - 如果消息与你的领域无关 → should_speak = false
  - 如果你观察到严重的事实错误或关键遗漏 → should_speak = true（即使不是你的主领域）

user: |
  新消息：{message_content}

  以 JSON 格式回复。不要回复其他内容。
  {
    "should_speak": true/false,
    "confidence": 0.0-1.0,
    "reason": "简短的理由"
  }
```

### 3.6 观察摘要（Observation Summary）

每个 Agent 维护一个私有的观察摘要——不与其他 Agent 共享。

**目的**：让 Agent 在不发言时仍然「在场」——追踪对话进展，积累背景知识，检测插嘴时机。

**内容结构**：

```json
{
  "session_goal": "设计 acp vs cp 的性能 benchmark",
  "key_facts": [
    "ZP 要做专业的性能对比测试，不是写集成测试代码",
    "测试场景：大文件 + 多小文件",
    "acp coder 建议 10000+ 小文件体现 aio context 优势",
    "测试 Agent 指出 fsync 策略差异比文件数量更重要",
    "⚠️ 尚未确定评判标准"
  ],
  "decisions": [],
  "open_questions": [
    "benchmark 的评判标准是什么？",
    "是否需要统计 CPU/内存使用？"
  ],
  "potential_interrupts": [
    "评判标准尚未确定 → 可以插嘴提醒"
  ]
}
```

**更新机制**：每条新消息到达时，用低成本模型更新摘要（增量更新，不是重新生成）。摘要只保留最近 N 条关键信息（如 20 条），旧信息自动淘汰。

### 3.7 沉默与插嘴的平衡

Agent 保持沉默不等于离线。沉默 Agent 在后台持续做两件事：
1. 更新观察摘要
2. 在相关性判断时评估「是否有必须打破沉默的理由」

**打破沉默的触发条件**（任一满足即可）：

| 条件 | 示例 |
|------|------|
| 观察到事实错误 | acp coder 说「cp 比 acp 快 3 倍」但实际测试显示是 1.5 倍 |
| 观察到关键遗漏 | 讨论 benchmark 但没人提 fsync 差异 |
| 观察到方向偏离 | PM Agent 发现大家开始讨论实现细节而非澄清需求 |
| 被其他 Agent @ | 强制回复 |
| 人类发出全局信号 | 「有没有人不同意？」→ 之前沉默但持反对意见的 Agent 应发言 |

**插嘴频率控制**：同一 Agent 在短时间内（如 3 条消息内）只能插嘴一次，避免一个 Agent 霸屏。

## 四、并发控制

### 4.1 先到先发言 + 后到看情况

```
Agent A 发送回复 ──→ 立刻推送到群聊
    │
    │  Agent B 正在生成回复中...
    │  发现群聊里多了 Agent A 的回复
    │      │
    │      ├─ A 已经说了 B 想说的 80% → 取消自己的回复
    │      ├─ A 说了相关内容但 B 有重要补充 → 重写回复，引用 A
    │      └─ A 和 B 说的完全不是一回事 → 继续发送
```

**实现**：回复生成完成后，在发送前做一次去重检查（同样用 nano 模型判断是否需要调整/取消）。

### 4.2 并发回复的排序

如果多个 Agent 同时完成回复生成（在去重检查之前），按以下优先级排序：

1. 被 @ 的 Agent 先发言
2. 相关性 confidence 高的先发言
3. Agent ID 字典序（兜底）

## 五、技术约束

### 5.1 模型使用策略

| 组件 | 模型级别 | 成本要求 |
|------|---------|---------|
| 相关性判断器 | nano 级（GPT-4.1 nano / GLM 最小版） | < $0.10 / 百万 token |
| 回复生成器 | 主力模型（Qwen / GLM / Claude） | 按需，不做额外限制 |
| 观察摘要更新 | nano 级 | < $0.10 / 百万 token |
| 去重检查 | nano 级 | 同上 |

**设计原则**：相关性判断和摘要更新占调用量的 80%+，必须用最便宜的模型。回复生成只占 10-20%，可以用好模型。

### 5.2 上下文管理

- 每个 Agent 独立维护自己的上下文窗口
- 全量聊天记录保留在 session 级别（不丢消息）
- Agent 回复生成时，输入「完整聊天记录」还是「压缩摘要」，由上下文窗口剩余空间决定
- 观察摘要独立于聊天记录，不占用主上下文

### 5.3 语言和平台

- Python（与 PLAN.md 一致）
- 配置：TOML
- LLM 适配层：复用 PLAN.md 的 OpenAI 兼容 API 适配层
- Agent 角色定义：独立的 `agents.toml`

### 不包含（v0.2+）

- 观察摘要的长期记忆（跨 session）
- Web UI
- 与 PLAN.md 中 Leader-Worker 模型的集成

```
1. 创建 session，加入 2 个 Agent + 1 个人类
2. 人类发送「我想给 acp 做一个 benchmark，你们怎么看」
3. PM Agent 发言澄清需求
4. 测试 Agent 提出方案
5. 人类 @ 测试 Agent 追问细节
```

- 核心难题识别：「谁该说话」→ 拆分为相关性判断（nano 模型）+ 回复生成（主力模型）两步
- 沉默 Agent 通过观察摘要保持「在场」，在检测到错误/遗漏时打破沉默
- Agent 间互相 @ 作为标准交互模式
- 并发回复由去重检查处理，避免多个 Agent 说同样的话
- 两种模型（群聊 + Leader-Worker）共享角色定义，但 v0.1 独立实现
